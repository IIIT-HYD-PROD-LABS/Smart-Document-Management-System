# Plan 17-04: Wave 3 Celery + Gmail Ingestion Wiring

**Status:** SHIPPED 2026-05-22
**Phase:** 17
**Wave:** 3
**Goal:** Wire the Wave 2 extractor into the two existing ingestion paths (Celery upload + Gmail) so notice extraction runs automatically without changing the routes or the UI.

## Delivered

1. **Celery wiring** (`backend/app/tasks/document_tasks.py`).
   - New helper `_run_phase17_extraction(db, *, document_id, notice_id, user_id, extracted_text)` at module top.
   - `process_document_task` calls the helper after the standard AI extraction step, gated on `if getattr(doc, "notice_id", None):` (D-23). Failure is non-fatal: the helper traps every exception, marks `notice.extraction_status='failed'`, and returns (D-09).
   - First-upload-wins (D-12): `should_skip_extraction(notice)` returns True for any `extraction_status in ('accepted', 'superseded')`. The supplementary upload still leaves a `file_attached` activity row.

2. **Gmail wiring** (`backend/app/email/services/ingestion_service.py`).
   - In the `is_compliance and confidence == 1.0` branch, the extractor is called BEFORE notice creation (D-24).
   - When `route_or_apply` returns `'apply'`, the extracted `notice_number` and `authority` are pulled into the ComplianceNotice constructor; otherwise the original sender-derived authority + `GMAIL-{message_id}` fallback applies (D-09).
   - After `db.flush()`, `apply_extraction_to_notice` persists the envelope onto the notice regardless of routing decision, and the `NOTICE_AUTO_CREATED` audit row gains a `phase17_extraction_action` field for cross-reference with the preceding `NOTICE_AI_EXTRACT` audit row (D-24, D-16).

3. **Routing + apply helper** (`backend/app/compliance/services/extraction_routing_service.py`).
   - `apply_extraction_to_notice(db, notice, envelope, decision)` is the single mutation point. Writes `extracted_fields`, `extraction_confidence`, `extracted_by_provider`, `extracted_at`, `extraction_status='completed'`. Enqueues to Phase 10 review queue when `decision['action'] == 'review_queue'`.
   - `should_skip_extraction(notice)` returns True for `extraction_status in ('accepted', 'superseded')`.
   - `_enqueue_for_review(db, notice, envelope, decision)` maps the Phase 17 envelope onto Phase 10's `enqueue_low_confidence` signature (predicted_authority from the envelope's authority field). Bridge code; the actual review-queue UI is unchanged.

## Decision deltas during Plan 17-04

- **`_run_phase17_extraction` lives in `document_tasks.py`, not in a new module.** Keeps the Celery path's full failure handling close to the task body. Splitting it into its own module would have forced the import-or-skip guard pattern across two files for no observable benefit.
- **Mock-patch path correction.** Tests originally tried `patch.object(ingestion_service, "authority_from_sender", ...)` and `"log_audit_event_strict"`. Both are local-imports inside the function body; the correct patch target is the source module (`app.email.classifier_rules.authority_from_sender` and `app.services.audit_service.log_audit_event_strict`). Test bug, not code bug; the production code's local-import pattern is intentional (avoids circular imports through `app.compliance`).
