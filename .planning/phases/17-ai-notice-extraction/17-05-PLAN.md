# Plan 17-05: Wave 4 Router Endpoints

**Status:** SHIPPED 2026-05-22
**Phase:** 17
**Wave:** 4
**Goal:** Expose the Wave 2 extractor and Wave 3 wiring through three HTTP endpoints with the correct gates, rate limit, and PII redaction. After this wave the backend is feature-complete; only the UI rewrite remains.

## Delivered

Three endpoints appended to `backend/app/compliance/routers/notices.py`:

1. **`POST /api/compliance/notices/extract-preview`** (D-19, D-22)
   - Multipart file upload. Validates content type against `_ALLOWED_UPLOAD_CONTENT_TYPES` (PDF, JPG, PNG).
   - Runs OCR + extraction synchronously; no notice row, no document row persisted.
   - Permission gate: `NOTICE_AI_EXTRACT`.
   - Rate limit: `@limiter.limit("12/minute")` per tenant (same limiter Phase 16 uses).
   - Failure modes: 400 (bad content type), 412 (no AICredential, with `{code, message, settings_path}` body for the UI banner), 415 (OCR could not read the file), 422 (no text extracted, or OUT_OF_SCOPE sentinel), 502 (provider returned an unparseable response).
   - Success: returns `ExtractPreviewResponse {envelope, decision}` so the UI can render the form pre-fill and the per-field confidence badges in one round trip.

2. **`GET /api/compliance/notices/{notice_id}/extraction`** (D-20)
   - Returns the persisted extraction artefact for a notice.
   - Permission gate: `NOTICE_VIEW` (every reader of the notice can see the provenance).
   - Returns `ExtractionResponse {notice_id, extraction_status, extraction_confidence, extracted_by_provider, extracted_at, envelope}`.

3. **`POST /api/compliance/notices/{notice_id}/accept-extraction`** (D-21)
   - Body: `AcceptExtractionPayload` (1-14 items, each `{field, value, accept_as_is}`).
   - Permission gate: `NOTICE_AI_EXTRACT` (dependency) plus inline check on `NOTICE_CREATE` (which is the existing edit-notice gate — Phase 9 used NOTICE_CREATE as the manual-edit verb on PATCH `/notices/{id}`; we mirror it here).
   - 409 Conflict if `notice.extraction_status` is not `completed` (avoids accepting twice) or `accepted` (idempotent re-accept).
   - Per accepted field: copies the value onto the canonical notice column (`notice_number`, `authority`, `received_date`, `response_deadline`, `tax_demand`, `interest`, `penalty`, `total_liability`) and writes one immutable audit row (`action='notice_ai_extract_accepted'`) carrying SHA-256 of the original-extracted value, SHA-256 of the accepted value, and `was_edited: bool` per D-17.
   - After all items processed: flips `notice.extraction_status='accepted'` and commits.

## Decision deltas during Plan 17-05

- **`accept-extraction` gate uses `NOTICE_AI_EXTRACT` dependency + inline `NOTICE_CREATE` check, not two dependencies.** Two `require_compliance_permission` dependencies on one handler is supported by FastAPI but the failure modes interleave and the error message becomes generic. The inline second check lets us return a tailored 403 ("Role lacks permission to update notice fields") if a future role gets NOTICE_AI_EXTRACT but not NOTICE_CREATE. The contract is identical to PATCH `/notices/{id}` which Phase 9 gates on NOTICE_CREATE as the edit verb.
- **Tests call handlers via `__wrapped__` to bypass `@limiter.limit`.** slowapi's decorator rejects a MagicMock request with `Exception: parameter 'request' must be an instance of starlette.requests.Request`. The unwrapped path tests the business logic directly; rate-limit presence is asserted structurally (module source contains `@limiter.limit("12/minute")`). End-to-end rate-limit behaviour is verified by the smoke script in Plan 17-07.
- **`accept-extraction` does NOT block re-accept when `extraction_status='accepted'`.** Idempotent re-accept is allowed; the audit rows accumulate and the most recent value wins. This mirrors how Phase 12's response approval workflow handles re-approval after a revision.
