# Phase 10 Plan 01 — Review Queue Backend

## Wave: 1 of 3 (within v2.0 ship of Phase 10)

## Goal

CLASS-04 demands that low-confidence (<0.75) classifications route to a human
review queue rather than auto-assign. v2.0 ships the **infrastructure** so the
hook is in place when v2.1's BERT fine-tune lands real low-confidence
predictions.

## Scope

**In scope:**
1. `NoticeReviewQueue` ORM mapping migration 0020's `notice_review_queue` table
2. Pydantic schemas: `ReviewQueueOut`, `ReviewQueueAssignRequest`, `ReviewQueueAssignResponse`
3. `review_queue_service` with three operations:
   - `enqueue_low_confidence(notice, predicted_authority, predicted_authority_confidence, predicted_type_id, predicted_type_confidence, model_version, reason)` — idempotent (UNIQUE on `notice_id`)
   - `list_pending(client_id, limit=50, offset=0)` — RLS-scoped
   - `assign_reviewer_label(queue_id, user_id, authority, type_id)` — sets `reviewer_*` fields, updates ComplianceNotice's authority/notice_type_id, writes NoticeActivity (mutable) + AuditLog (immutable)
4. Router `/api/compliance/review/`:
   - `GET /pending` → list of pending review items (paginated)
   - `GET /{id}` → single review item detail
   - `PATCH /{id}/assign` → reviewer assigns final authority/type
5. Wire hook in `compliance_tasks.classify_and_score_notice`: when both BERT
   classifiers eventually populate non-NULL confidences AND either is below
   `CONFIDENCE_THRESHOLD = 0.75`, call `enqueue_low_confidence`. **For v2.0 the
   hook is wired but never fires** because BERT confidences stay NULL. v2.1
   activates it.
6. Tests:
   - `test_review_queue_service.py` — enqueue idempotency, RLS scoping, assign updates parent notice, audit + activity rows written
   - `test_review_queue_endpoints.py` — auth, RBAC (`NOTICE_VIEW`/`NOTICE_REVIEW`), pagination
   - `test_classify_and_score_task.py` extension — when confidences below threshold are passed, queue insertion fires; when NULL (v2.0 default), no insertion
7. RBAC: a new permission `NOTICE_REVIEW` granted to `compliance_head`,
   `ca_consultant`, `legal_team`. Reuses Phase 9 permission registry pattern.

**Out of scope:**
- BERT classifier production (deferred to v2.1)
- Frontend review queue page (Plan 10-03)
- Auto-escalation logic (Plan 10-02)

## Risks

- **Risk:** Idempotent enqueue via unique constraint on `notice_id` could race
  on rapid re-classify. **Mitigation:** Use `ON CONFLICT (notice_id) DO UPDATE`
  via SQLAlchemy `insert(...).on_conflict_do_update(...)` so the most recent
  prediction always wins.
- **Risk:** Assigning reviewer label mutates the parent ComplianceNotice
  (authority + notice_type_id). **Mitigation:** Service layer is the single
  point of mutation (Phase 9 D-D pattern); all writes happen in one
  transaction with audit + activity rows.
